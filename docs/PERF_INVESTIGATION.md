# NDLOCR-Lite 性能調査 統合レポート

**対象**: RTX 3070 / WSL2 Ubuntu / CUDA 13 / ONNX Runtime 1.31.1
**対象コード**: `HEAD` (`0b8b2c1` 時点の `src/ocr.py` / `src/deim.py` / `src/parseq.py` / `src/ort_provider.py`)
**計測日**: 2026-11-27
**目的**: (1) 12 ページ連続処理の工程別ボトルネック特定、(2) FP32 出力完全一致を維持したまま効く最適化の優先順位付け、(3) FP16 / TF32 の実現可能性の事前検証

> 計測はすべて**リポジトリ非改変**のモンキーパッチ・ハーネスで実施（`git status` クリーン）。
> 数値は特記なき限り中央値相当。同一条件でも ±5〜10 % のばらつきがあるため、差が 5 % 未満のものは「有意差なし」と扱う。

## 0. サマリ

### 0.1 現状の時間構造

| フェーズ | 実測 | 支配要因 |
|---|---:|---|
| プロセス起動 → 4 モデル準備完了 | **5.6 s** | CUDA EP のセッション生成 3.95 s（うち rec100 2.01 s） |
| ＋ 初回推論（cuDNN カーネル探索） | **+0.8 s**（DEIM だけで 1.15 s） | `cudnn_conv_algo_search=HEURISTIC` |
| （パッチキャッシュが無い初回のみ） | **+8.4 s** | 動的バッチ化 + 検証セッション |
| 定常 12 ページ（batch=32） | **2.48 s** | PARSeq 1.43 s（58 %）/ DEIM 0.46 s（19 %）/ XML 0.23 s |
| 定常 12 ページ（batch=64） | **2.33 s** | 固定費の償却が進む |

### 0.2 結論

1. **最大の構造的問題は「1 回の推論呼び出しあたり約 25 ms の固定費」**。PARSeq は 12 ページで 29 回呼ばれ、`batch=1` でも `batch=8` でもほぼ同じ 20〜23 ms かかる（GPU 計算ではなくカーネル起動が支配）。固定費は定常時間の **約 3 割**。
2. **初期化の支配項は ORT のグラフ最適化ではなく CUDA EP のパーティション/カーネル準備**（`ORT_ENABLE_ALL − DISABLE_ALL` は 16〜364 ms しかない）。したがって `optimized_model_filepath` は**期待したほど効かない**（実測: init −1.1 s / 定常 +1.2 s で正味ゼロ、さらに出力が 0.001 変化）。
3. **安全に効く順**: ①モデル初期化の並列化＋warm-up（−1.5 s/実行）→ ②バッチ 64 既定化（−0.16 s）→ ③CUDA Graph + IOBinding（−0.4〜0.5 s、出力 bit 一致）→ ④CPU 側 XML/PDF 工程（−0.2 s）→ ⑤クロスページバッチ（−0.4〜0.6 s、要設計変更）。
4. **FP16 は「GPU は速いがパイプラインは遅い」**。呼び出し単体では 1.45〜1.56× 高速だが、出力 logits が fp16 のままだと Python 側 `argmax` が 0.57 ms → **28 ms** に膨張し、全体では +10〜19 % の純損失。さらに素朴変換では文字一致率が 50〜61 % まで崩壊し、rec100 で NaN、DEIM で座標破綻する。**FP32 完全一致要件下では現行方式の FP16 は不可**。
5. **TF32 は −5.2 %** だが行単位で 1.1〜1.3 % の差が出る。完全一致要件では不可（現行の `use_tf32="0"` は正しい。ORT 既定は TF32 有効なので明示設定が効いている）。

### 0.3 期待できる改善幅（12 ページ、初期化込み）

| 段階 | 実測/試算 | 速度 |
|---|---:|---:|
| 現状（batch=32、直列 init） | 8.4〜10.2 s | 1.0× |
| 段階 1（並列 init + warm-up + batch 64） | **5.7〜6.2 s** | 1.4〜1.5× |
| 段階 2（+ CUDA Graph + IOBinding + XML 工程） | **≈ 5.0 s**（試算） | 1.7× |
| 段階 3（+ クロスページバッチ） | **≈ 4.6 s**（試算） | 1.9× |

## 1. 計測条件と再現方法

### 1.1 ハードウェア / ソフトウェア

| 項目 | 値 |
|---|---|
| GPU | NVIDIA GeForce RTX 3070 8 192 MiB（driver 617.42、Ampere sm_86） |
| CPU / RAM | AMD Ryzen 7 5800X（16 vCPU）/ 15 GB（WSL2） |
| OS / Python | WSL2 Ubuntu / CPython 3.12.16 |
| ONNX Runtime | `onnxruntime-gpu 1.31.1` + CUDA 13 EP（pip 配布の nvidia-* ホイール） |
| 入力 | 同梱 `resource/` の 5 画像を循環させた **12 ページ PDF**（150 dpi、`--pdf-page-output` 既定） |
| 出力 | PAGE 別 XML / JSON / TXT ＋ テキスト層 PDF |

### 1.2 計測手法

- `time.perf_counter()` による関数ラッパ（スレッド集計はロック付き）。`ocr` / `deim` / `parseq` / `ET` / `pypdfium2` の各関数を実行時にラップするだけで、**ソースは変更しない**。
- ORT の `InferenceSession.run` をクラスレベルでラップし、入力形状から **モデル別・バッチサイズ別**に集計。
- `cProfile`（定常 1 パス）と ORT の `enable_profiling`（ノード単位の provider 帰属）を併用。
- 単体計測（`np.argmax` の dtype 別コストなど）は入力テンソルだけを差し替えて比較。

### 1.3 注意点

- WSL2 はアイドルで自動停止し `/tmp` が消えるため、ハーネスは `/tmp/ndlocr-probe`（実行時）＋ `/root/work/tmp/probe-mirror`（永続ミラー）に配置。レポート・変換モデルはリポジトリ外（`/root/work/tmp/…`）に保存した。
- 12 ページは 5 画像の循環であり、実運用の文書分布とは行数・文字数が異なる。**相対比較には有効、絶対値は目安**。
- 計測はすべて CUDA 13 / ORT 1.31.1 / WSL2 の単一構成。Windows ネイティブではカーネル起動レイテンシが小さいため、固定費由来のボトルネックは相対的に小さくなる可能性がある（未検証）。

| 初回推論のカーネル探索（steady との差）DEIM | **1 145** | cuDNN HEURISTIC の autotune |
| 同 rec100 / rec30 / rec50 | 151 / 48 / 9 | PARSeq はほぼ探索なし |
| **OCR 経路の直列 init 合計**（パッチ済み・キャッシュヒット） | **4 258** | det 959 + rec30 592 + rec50 751 + rec100 1 956 |
| パッチキャッシュ初回の追加 | **+8 400** | `onnx.load`×2 + パッチ + 保存 + CPU 検証セッション×2 |

| **→ 初回推論（DEIM 探索）まで** | **6 416** | +680（DEIM warm-up）+136（rec30） |

### 2.2 読み取れること

- **`ORT_ENABLE_ALL` の最適化コストは無視できる**（合計 0.4 s 未満、rec100 では負）。「最適化に数秒かかっている」という想定は本環境では誤り。支配しているのは **CUDA EP の初期化（パーティション分割＋カーネル準備）** で、`DISABLE_ALL` でも 0.27〜2.09 s かかる。
- セッション生成時間はほぼモデルのノード数に比例（4.4 k ノード → 0.63 s、23 k ノード → 2.01 s）。
- **rec100（24×768）は 12 ページ処理で一度も推論されない**（後述: `PRED_CHAR_CNT` が 2/3 のみ）。それでも初期化 1.96 s を毎回払っている。
- 初回カーネル探索 1.3 s は「1 ページ目の遅さ」として現れる（1 ページ目のみ 1 550 ms、以降 70〜500 ms）。

### 2.3 実測した短縮手段

| 手段 | 実測 |
|---|---|
| 4 モデルの**並列構築**（`ThreadPoolExecutor(4)`、構築直後に 1 回 warm-up） | 直列 3.68 s → **2.50 s（1.47×）**。全セッションが CUDA EP、argmax 一致 |
| 並列構築＋`optimized_model_filepath` キャッシュ | init **1.94〜2.59 s** まで短縮するが、**定常側が +1.2 s 悪化**（後述） |
| バッチ・モデル準備の sidecar メタ化（size+mtime+hash） | sha256 18–22 ms ×3 ＋ `onnx.load` 30–44 ms ×2 を削減 → **0.2〜0.3 s** |

## 4. ボトルネック構造（固定費モデル）

```
1 回の PARSeq 呼び出し ≈ 25 ms（固定） + 0.75〜1.05 ms × 行数
12 ページの実績      = 29 回 × 25 ms  ≈ 730 ms  … 定常 2.48 s の 29 %
```

- 固定費の正体は**カーネル起動**。モデルは 9 k〜23 k ノードで、デコーダが 31/51/101 ステップに展開されているため 1 回の推論で 3 500 個規模のノードが走る。WSL2 の起動レイテンシ（数 µs × 3 500）が支配し、**batch 1 と batch 8 がほぼ同じ時間**になる。
- したがって効くのは「**呼び出し回数を減らす**」「**1 回あたりの固定費を消す（CUDA Graph）**」の 2 方向のみ。前処理やデコードの最適化は数 % に留まる。

## 5. 実測した最適化候補

### 5.1 ORT `optimized_model_filepath` キャッシュ — **不採用**

| 指標 | 実測 |
|---|---|
| セッション生成 | rec30 469 → **147 ms（3.2×）**、rec100 1 820 → **429 ms（4.3×）** |
| 固定 shape での推論時間 | 46.4 → 46.3 ms（**同等**） |
| 出力一致（モデル単体） | `max_abs_diff = 0.0`、argmax 一致 |
| **12 ページ E2E** | init **−1.1 s** / 定常 **+1.2 s**（3 回反復で再現）→ **正味ほぼゼロ** |
| 出力差分 | **12 頁中 2 頁で `TEXTBLOCK CONF` が 0.402 → 0.403**（TXT / JSON は一致） |

理由: 保存されるのは EP パーティション**前**のグラフで、ロード時に再度パーティションが走る。しかも `ORT_DISABLE_ALL` で読み込むため shape ごとの初回セットアップが定常側へ移る。さらに 0.001 の数値差が出るため「完全一致」要件と両立しない。

### 5.2 並列初期化 + warm-up — **採用（最優先）**

- 4 モデルを `ThreadPoolExecutor(4)` で構築し、**構築したスレッド内でそのまま 1 回推論**（warm-up）する。
- 実測: 直列 3.68 s → **2.50 s（1.47×）**。CUDA EP 使用・出力一致を確認。
- 効果: 12 ページ実行で **−1.5 s（総時間の約 20 %）**。初回ページの +1.3 s スパイクも消える。
- リスク: 低。GPU 文脈の競合は 3 回の反復で再現せず。warm-up を入れると**初期化合計は増える**が、初回推論の探索コストを他モデルの構築中に隠せる。

### 5.3 既定バッチ 32 → 64 — **採用（即効）**

| 設定 | 定常 12p | VRAM 最大 |
|---|---:|---:|
| b32（現行） | 2.482 s | 2 587 MiB |
| **b64** | **2.325 s（−6.3 %）** | 2 837 MiB |
| b96 | 2.304 s（−7.2 %） | 3 349 MiB |

- 出力は b32 とバイト一致（TXT/XML/JSON 36/36）。
- b96 以上は伸びが鈍く VRAM だけ増えるため **64 が妥当**。VRAM 8 GB で他モデルを載せる場合は 32 のままでも可。

### 5.4 CUDA Graph（静的バケット）+ IOBinding — **採用候補（効果大）**

| batch | 通常 | CUDA Graph | 倍率 | 出力 |
|---:|---:|---:|---:|---|
| 1 | 20.0 ms | **6.3 ms** | **3.16×** | bit 一致 |
| 4 | 20.9 ms | 8.8 ms | 2.39× | bit 一致 |
| 8 | 22.9 ms | **12.5 ms** | **1.84×** | bit 一致 |
| 16 | 30.2 ms | 18.7 ms | 1.62× | bit 一致 |
| 32 | 43.9 ms | **32.6 ms** | **1.34×** | bit 一致 |
| 64 | 75.5 ms | 60.5 ms | 1.25× | bit 一致 |

- 必要条件: **静的 shape**（動的バッチ不可）、**IOBinding 必須**、`cudnn_conv_algo_search` は `DEFAULT`（HEURISTIC は capture 不可）、全ノードが CUDA EP。
- 実装案: バケット {8, 16, 32, 64} の静的モデルを用意し、呼び出し行数を切り上げてパディング。
  - 例: 5 行 → b8 バケット（12.5 ms）で現行の 27 ms より速い。13 行 → b16（18.7 ms）< 30 ms。
- 効果試算: 現行 730 ms/pass の固定費が ≈ 250 ms/pass へ → **−0.4〜0.5 s/pass（−18 %）**。
- IOBinding 単体（動的バッチのまま）でも **46.4 → 42.7 ms/呼（−8 %）**。
- リスク: 中。`cudnn_conv_algo_search=DEFAULT` によりカーネル選択が変わり得るため、**全コーパスのゴールデン差分 + NaN チェックが必須**。VRAM はバケット数分増える（rec100 は使われないため対象外にして削減可）。

### 5.5 前処理（`preprocess_batch`）— **採用（安全・小効果）**

| 方式（32 枚処理） | 時間 |
|---|---:|
| 逐次（現行の `_preprocess_single` 相当） | **1.40 ms** |
| 現行（毎回 `ThreadPoolExecutor(4)` を生成） | 8.04 ms |
| 永続 `ThreadPoolExecutor(4)` | 7.19 ms |
| 永続 1 ワーカー | 2.65 ms |

- **スレッド化はこのワークロードで 5〜8 倍のペシミゼーション**（GIL + 小さすぎるテンソル）。n=8/16/64 でも同傾向。
- `np.ascontiguousarray(resized[:, :, ::-1])` → **`cv2.cvtColor(resized, cv2.COLOR_BGR2RGB)`** で **2.1×**、200 枚で `array_equal` 完全一致。
- 効果: 前処理段 187 ms/pass → ≈ 15 ms/pass。ただし支配的でないため **E2E では −0.05 s 程度**（実測誤差範囲）。**「他環境での退行防止」と「次段のプリフェッチ設計を可能にする」ことが主目的**。

### 5.6 クロスページ・バッチ収集 — **採用候補（設計変更）**

- 12 ページで 29 回の呼び出しを、**64 行単位に束ねて 8〜10 回**へ。
- 試算: rec30 313 行/パス → 5 回 × 75.5 ms = 378 ms（現行 771 ms）、rec50 214 行 → 4 回 ≈ 388 ms（現行 591 ms）→ **−0.4〜0.6 s/pass**。
- 実装上の必須事項:
  - `RecogLine.__lt__` が `idx` 単独比較のため、**`(page, idx)` の複合キー**にしないとページ跨ぎで順序が壊れる。
  - `RecogLine.npimg` はページ配列のビューなので、**保持ウィンドウを K ページ（3〜4）に制限**（12 頁分保持で A4@300dpi × 12 ≈ 300 MB）。
  - 出力は `{(page, idx): text}` で戻し、`_run_ocr_on_image_array` 側は事前計算テキストがあれば `process_cascade` をスキップ。
- リスク: 中。バッチ構成が変わると `TEXTBLOCK CONF` が 0.001 変わる可能性（要ゴールデン差分）。

### 5.7 CPU 側 XML / PDF 工程 — **採用候補（一部はバイト一致）**

| 対象 | 実測 | 施策 | 効果 | 出力への影響 |
|---|---:|---|---:|---|
| `eval_xml`（xy-cut） | 227 ms | `calc_min_span` / `calc_hist` の純 Python 化・累積和化（1.5〜1.8×） | −60〜90 ms | **バイト一致**（`ORDER` は整数 rank） |
| `build_markdown_text_from_page` | 38 ms | CLI では呼ばない（GUI のみ必要） | −38 ms | なし（GUI は再計算している） |

## 6. FP16 / TF32 の実現可能性

### 6.1 ノード調査（静的解析）

| モデル | ノード | fp16 変換可（float） | FP32 保持推奨 | 主要リスク op |
|---|---:|---:|---:|---|
| DEIMv2（800²） | 4 381 | 1 645 / 2 083（79 %） | 231（Cast 631 本） | `GridSample`×12、`TopK`×3、`Range`×2、`Resize`×5、`anchors[1,13125,4]` |
| PARSeq 24×256 | 9 397 | 4 484 / 5 033（89 %） | 414（Cast 994 本） | LayerNorm eps=1e-5（fp16 最小正規化数 6.1e-5 未満）、Erf×53、Softmax |
| PARSeq 24×384 | 11 986 | 5 508 / 6 178（89 %） | 502（Cast 1 223 本） | 同上 + T=51 の展開済み AR ループ |
| PARSeq 24×768 | 22 936 | 10 408 / 11 628（90 %） | 902（Cast 2 223 本） | 同上 + リテラル `1` 形状 1 043 個 |

- 事前仮説「`ReduceMax(axes=[0])` がバッチ軸を潰す」は**誤り**。DEIM の縮約は `axes=[-1]`（画像内）。バッチ不可の原因は **`anchors` 初期化子が `[1, 13125, 4]` で固定**されている点。
- `NonMaxSuppression` / `RoiAlign` / `NonZero` は全モデルに存在せず、CUDA fp16 の古典的フォールバック要因は回避されている。
- 形状系 op（Slice/Gather/Concat/Reshape）は int64/bool が多く、fp16 変換の影響を受けない。

### 6.2 実測（12 ページ定常・5 画像）

| 構成 | 12p 定常 | 5 画像 | 文字一致率（行） | 読み順一致 | 行数差 | VRAM 最大 |
|---|---:|---:|---:|---:|---:|---:|
| **FP32（既定, use_tf32=0）** | **2.482 s** | 1.822 s | 基準 | 基準 | 0 | 2 587 MiB |
| **FP32 + TF32（use_tf32=1）** | **2.354 s（−5.2 %）** | 1.843 s（±0） | **98.9 % / 98.7 %** | 100 % / 100 % | 0 | 2 583 MiB |
| **FP16（PARSeq のみ）** | 2.725 s（+9.8 %） | 2.364 s | **61.1 % / 54.7 %** | 22.0 % / 16.9 % | +16 / +5 | 2 187 MiB |
| **FP16（DEIM + PARSeq）** | 2.944 s（+18.6 %） | 2.498 s | **50.8 % / 47.6 %** | 22.0 % / 16.9 % | +14 / +3 | 1 929 MiB |

補足:
- TXT 完全一致: TF32 **10/12 頁**、FP16(PARSeq) 7/12、FP16(全部) 2/12。
- FP16 の **rec100 で 2 307 万要素が NaN**。rec30 は NaN なしだが argmax 不一致 4/32 行。
- FP16 の DEIM は NaN なしだが **boxes の最大誤差 1 197 px**（座標系破綻）。`GridSample` 12 ノードが CPU へ、cuDNN から "No execution plans support the graph" も発生。

### 6.3 「GPU は速いのにパイプラインは遅い」原因（重要）

| 計測（batch 32、呼び出し単体） | FP32 | FP16 | 比 |
|---|---:|---:|---:|
| rec30（24×256） | 49.5 ms | 31.8 ms | **1.56×** |
| rec50（24×384） | 59.5 ms | 41.0 ms | **1.45×** |
| rec100（24×768） | 133.7 ms | 88.5 ms | **1.51×** |
| `np.argmax`（32, 31, 7142） | **0.57 ms** | **28.16 ms** | **0.02×** |
| `np.argmax`（32, 101, 7142） | 4.10 ms | 91.96 ms | 0.04× |
| 同上（fp16 → `astype(np.float32)` してから argmax） | — | 3.2 + 0.6 ms | — |

**結論**: GPU 側には 1.45〜1.56× の余地があるが、**出力 logits が fp16 のままだと Python 側 `argmax` が 28 ms に膨張**し（推論短縮分の 10〜20 倍）、パイプライン全体では純損失。FP16 を入れるなら **logits を fp32 で返す**ことが必須条件。

### 6.4 変換コンバータの実装上の問題

- `onnxruntime.transformers.float16.convert_float_to_float16` に `op_block_list` / `node_block_list` を渡すと、**FP32 保持ノードの境界に同名の Cast 値を二重生成**し、`Duplicate definition of name (..._cast_to_fp32)` で invalid model になる（本環境で再現）。
- 回避策: 変換後に値名を一意化する de-dup パスを入れる、または `keep_io_types=True` にして境界を自前で挿入する。
- 参考: ORT 1.31.1 の既定 `op_block_list` は 28 種（`NonMaxSuppression`, `TopK`, `RoiAlign`, `Range`, `CumSum`, `Min`, `Max` 等）を含む。

### 6.5 推奨設計（将来 `--precision fp16` を作る場合）

1. **既定は FP32 のまま**（`use_tf32="0"`）。
2. **対象は PARSeq のみ**、DEIM は FP32 固定（座標・`GridSample`・`TopK`・CPU フォールバック・アンカー固定）。
3. 変換条件: `keep_io_types=True`（**logits は fp32 で出力**）、`op_block_list = {LayerNormalization, Softmax, Pow, Sqrt, ReduceMean, Div, Erf}`、変換後 de-dup。
4. 期待値: 推論 1.43 s → **0.95〜0.99 s**、decode を fp32 のまま保てれば **doc 2.48 → 2.05 s（−17 %）**、VRAM **−400 MiB**。
5. 受け入れ条件: 5 画像（通常 / `--enable-tcy`）＋ 3 ページ PDF で **TXT / XML / JSON が FP32 と完全一致**すること。argmax の同点反転で数行差が出る可能性があるため、完全一致が無理なら「差分 0 を要件から外す」判断が必要。
6. **速度目的では優先度低**。FP16 の価値は **VRAM −400〜−660 MiB**（8 GB で他モデルを同居させる用途）。
